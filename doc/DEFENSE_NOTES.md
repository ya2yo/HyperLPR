# 11/04 线下汇报 · 队员 2 汇报要点（一页纸）

> 对应 6 分钟框架中「静态划分」环节（约 1.5 分钟）＋ Part A 源码结构（背景后紧接着讲）。
> 原则：只讲三个数字、一张图、一个结论；细节留给提问。

## 一、我的 90 秒讲稿骨架

1. **应用与结构（30 秒）**：HyperLPR 是四阶段流水线——定位 → 对齐 → 识别 → 分类。
   我们把写死的 `run()` 拆成四个可独立调度的算子，这是"能划分"的前提。
   *其中只有对齐是纯几何运算，其余三个是 AI 推理。*
2. **切分点依据（30 秒）**：端侧花 19 ms 做定位+对齐，就把 385 KB 原图压成 9.75 KB 切片
   （削减 97.5%）；而占端侧 77% 算力的识别阶段，输入恰好只是这张切片——卸载它既省算力又不增流量。
3. **实验佐证（30 秒）**：7 图 × 4 策略 × 5 网络实测。5G 下 P1 全云端反而略快；
   POOR 弱网下 P2 比 P1 快 21 倍 → **没有全局最优的静态切分点，这就是 Part C 动态决策的依据**。

## 二、必须背下来的数字

| 数字 | 含义 | 出处 |
|---|---|---|
| **19 ms / 97.5%** | 端侧定位+对齐代价 / 载荷削减（385 KB → 9.75 KB） | §3.4 基线 |
| **21×** | POOR 弱网下 P2 相对 P1 的端到端加速（12308 → 585 ms） | §4.1 矩阵 |
| **92 ms / 142.6 MB** | 端侧四阶段总耗时（约单核跑满）/ 峰值内存 | §4 基线 |

## 三、预期提问与回答口径

**Q1 "网络是模拟的，可信吗？"**
→ 传输模型 `T = RTT/2 + Payload×8/BW` 是 MCC 标准口径（MAUI / CloneCloud 一脉），
五档参数取真实网络典型值；云侧用本地等价执行，是**保守上界**——真实云端更强只会让 P2 更好看。
队员 3 的 FastAPI 就绪后用 `--endpoint` 复跑同一矩阵做真实链路对照。

**Q2 "为什么不再把切片压小一点？"**
→ 做过 JPEG 质量扫描：q95 安全，q85 起困难样本识别即劣化（一致率 85.7% → 71.4%），
9.75 KB 是**不损失识别精度的下限**。顺带引出 Part C 新维度：按图像质量自适应选编码质量。

**Q3 "P2 和 P3 上传量几乎一样（9.75 vs 8.29 KB），为什么 P3 不行？"**
→ 实测 P3 识别一致率仅 42.9%（P2 为 7/7）——未做透视矫正的裁剪区识别质量崩了。
**对齐必须留在端侧**，0.7 ms 买来的是云端识别的正确性。

**Q4 "你的耗时数据和 dev 早期文档（det 占 48%）对不上？"**
→ 那是早期未实测的估计，我们已统一到实测口径并在报告标注修正：
实测 det 只占 20%，大头是识别（77%）。修正反而更有利——端侧代价更小、可卸载算力更多。

**Q5 "WSL 环境测的数据有代表性吗？数字会变吗？"**
→ 会波动 ±8%（共享 CPU 调度噪声），但我们每个组合重复 3 次取中位数，资源类指标
（内存 142.6 MB、CPU ~1 核、切片 9.75 KB）高度稳定；终期前在物理机复测一组对照。

**Q6 "载荷削减 97.5%，任务书要求 99%，没达标？"**
→ 99% 是任务书估计值。我们论证了 9.75 KB 是精度无损下限（Q2），
且按 P1 实际上传字节（JPEG 重编码 725 KB）算削减达 98.66%。中期报告将如实说明。
