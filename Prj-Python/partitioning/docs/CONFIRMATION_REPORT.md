## 1. 研究背景与意义

移动云计算（Mobile Cloud Computing, MCC）中，"计算划分"（Computation Partitioning）指把一个应用的执行切分到移动终端与云端：计算密集的部分卸载到云，终端只保留必须本地执行的部分。划分点选在哪里，直接决定三件事：

1. **端到端时延** = 端侧计算 + 上行传输 + 云侧计算 + 下行传输；
2. **网络流量**（运营商计费与弱网可用性）；
3. **隐私暴露面**（上传原图 vs 上传局部切片）。

静态划分（离线定死一个切分点）在网络稳定时有效，但真实移动网络会在 5G/WiFi/4G/弱网之间反复跳变，因此课程 Part C 要求进一步做**运行时动态自适应划分**。而动态决策的前提，是先把应用拆成可独立调度的算子，并拿到每个算子的真实耗时与数据载荷——这正是本课题 Part A 的工作。

## 2. 选定的应用程序：HyperLPR

- **定位**：开源中文车牌识别框架，支持单行蓝牌/黄牌、新能源、教练车、双层黄牌等；
- **技术栈**：Python 侧基于 ONNXRuntime（推理）+ OpenCV（图像处理），C++ 侧基于 MNN；
- **选型理由**：
  - 天然是**四阶段顺序流水线**（定位 → 对齐 → 识别 → 分类），切分点清晰；
  - 中间张量存在**数量级的体积落差**（原图 MB 级 → 车牌切片 KB 级），划分收益显著、易量化；
  - 纯 CPU 可跑（720p 单核 < 100 ms），端侧与云侧都能在同一台机器上复现，实验可控；
  - 跨平台（Linux/macOS/Android/iOS），贴近真实移动场景。

## 3. 应用程序源码模块结构

### 3.1 分层结构

| 层次 | 职责 | 关键源文件（Prj-Python/hyperlpr3/） |
|---|---|---|
| 接口层 | 对外暴露识别入口与 CLI/Web 服务 | `hyperlpr3.py`、`command/cli.py`、`command/serve.py` |
| 编排层 | 把四个算子串成有向级联流水线，负责张量与元数据流转 | `inference/pipeline.py`（`LPRMultiTaskPipeline`） |
| 算子层 | 检测/识别/分类的 ONNX 会话封装（前处理 → 推理 → 后处理） | `inference/multitask_detect.py`、`inference/recognition.py`、`inference/classification.py`、`inference/base/base.py`（`HamburgerABC`） |
| 数据层 | 图像几何变换、类型定义、词表 | `common/tools_process.py`、`common/typedef.py`、`common/tokenize.py` |
| 配置层 | 模型路径、运行时参数、初始化 | `config/settings.py`、`config/configuration.py` |

### 3.2 四个算子（可独立调度的切分单元）

| 阶段 | 类 | 输入张量 | 输出张量 | 备注 |
|---|---|---|---|---|
| Stage 1 目标定位 | `MultiTaskDetectorORT` | 原图 BGR（H×W×3） | 每车 14 维：框 4 + 置信 1 + 四角点 8 + 层标志 1 | 多任务 YOLO，同时回归框与角点 |
| Stage 2 几何对齐 | `get_rotate_crop_image` | 原图 + 四角点 | 车牌切片 48×160×3 | 透视变换，CPU 纯几何运算 |
| Stage 3 字符识别 | `PPRCNNRecognitionORT` | 切片 48×160×3 | 车牌号字符串 + 置信度 | CRNN + CTC，双层牌分段识别 |
| Stage 4 属性分类 | `ClassificationORT` | 切片 96×96×3 | 类别索引（蓝/黄/绿） | 仅在号码规则判不出类型时调用 |

### 3.3 数据流与切分点

```
原图 (数百 KB ~ 2 MB)
   │  Stage 1 目标定位       18.54 ms  (端侧算力 20.1%)
   ▼
四角点 (8 个整数)
   │  Stage 2 几何对齐        0.67 ms   (0.7%)
   ▼
★ 车牌切片 48×160×3 ≈ 9.75 KB     ← 黄金切分点：载荷骤降两个数量级
   │  ─ ─ ─ HTTP POST（P2 上传）─ ─ ─ ▶
   ▼
Stage 3 字符识别 + Stage 4 属性分类  71.09+1.74 ms (79.1%)  →  车牌号 / 类型 / 置信度
```

> 数据为本项目实测（WSL Ubuntu / Python 3.12 / ONNXRuntime，输入 1920×1080，7 图 × 4 策略 × 5 网络 × 3 次取中位数，完整 CSV：`benchmark_results.csv`）。
>
> **重要修正**：dev 分支早期文档记录的"Detector 19.2 ms 占 48%"与本项目实测不符——实测 Detector 只占端侧算力的 **约 20%**，真正的大头是 Stage 3 字符识别（约 **77%**）。这一修正反而**强化**了 P2 的合理性：端侧只需付出约 19 ms，就能把上传载荷从 385 KB 压到 9.75 KB，同时把 77% 的算力卸载到云端。配套矢量图见 `doc/dataflow.typ`。

### 3.4 端侧基线性能实测（Part A 验收交付）

在 WSL Ubuntu / Python 3.12 / ONNXRuntime 下，对 `test_img.jpg`（1920×1080）逐阶段独立计时 20 轮取均值，结果如下：

| 阶段 | 耗时(均值) | 标准差 | 端侧算力占比 |
|---|---|---|---|
| Stage 1 目标定位 | 18.54 ms | ±5.65 | 20.1% |
| Stage 2 几何对齐 | 0.67 ms | ±0.14 | 0.7% |
| Stage 3 字符识别 | 71.09 ms | ±25.99 | 77.2% |
| Stage 4 属性分类 | 1.74 ms | ±2.19 | 1.9% |
| **端侧合计** | **92.04 ms** | — | 100% |

**系统资源占用**：峰值常驻内存（RSS）**142.6 MB**；进程 CPU 占用率 **102.2%（占 32 核总 CPU，即约单核跑满）**。HyperLPR 端侧推理属内存轻量、单核可承载的负载，适合在算力受限的移动端运行。

**切分点论证**：端侧仅花 19.2 ms（Stage 1+2）完成定位与对齐，即可将上传量从 385 KB 原图压到 9.75 KB 切片（削减 97.47%，约 39 倍）；而占端侧 77% 算力的 Stage 3 识别，其输入仅是 9.75 KB 切片而非原图——卸载它到云端既不增加传输量、又省掉最贵的算力。完整脚本见 `Prj-Python/profile_baseline.py`，张量形态明细见 `doc/tensor_shapes.md`。

## 4. 划分方案设计（Part B）

| 策略 | 端侧执行 | 上传内容 | 云端执行 | 用途 |
|---|---|---|---|---|
| P0 全本地 | Stage 1–4 | 无 | 无 | 时延下界、零流量的对照组 |
| P1 全云端 | 无 | 完整原图（MB 级） | Stage 1–4 | 流量上界、弱网最差对照组 |
| P2 端侧检测+对齐 | Stage 1–2 | 矫正切片（≈9.75 KB） | Stage 3–4 | **黄金切分点** |
| P3 端侧仅检测 | Stage 1 | 矩形裁剪区（未矫正） | Stage 2–4 | 对比基准：验证"对齐放在端侧更划算" |

网络模型（issue #4 规约）：`T_net = RTT/2 + Payload × 8 / Bandwidth`，五档预设 5G(100 Mbps/10 ms)、WiFi(40/20)、4G(12/50)、3G_WEAK(1.5/150)、POOR(0.5/300)。

### 4.1 首轮实测结果（已跑通，非估算）

**端到端时延均值（7 张图，单位 ms）**

| 策略 | 5G | WiFi | 4G | 3G_WEAK | POOR |
|---|---|---|---|---|---|
| P0 全本地 | 83.5 | 78.2 | 68.2 | 59.5 | 65.9 |
| P1 全云端 | 112.2 | 150.9 | 237.0 | 954.6 | **2549.7** |
| P2 端侧检测+对齐 | 102.7 | 110.5 | 128.1 | 257.9 | **450.9** |
| P3 端侧仅检测 | 83.5 | 97.4 | 133.4 | 252.1 | 469.4 |

> P0 不含网络项，理论上与网络无关；实测在 59.5–83.5 ms 间波动，反映 WSL 共享 CPU 的测量噪声（单图多次取中位数后仍有 ±10 ms 抖动），正式报告中将补充纯物理机复测。

**上传载荷对比**

| 输入图 | 分辨率 | 原图 | P1 上传 | P2 上传切片 | 压缩比 |
|---|---|---|---|---|---|
| test_img.jpg | 1920×1080 | 385 KB | 725.34 KB | 9.75 KB | **74×** |
| 2.jpg | 1140×456 | 2031 KB | 102.24 KB | 15.59 KB | 6.6× |
| 1.jpg | 320×320 | 30 KB | 30.32 KB | 1.18 KB | 26× |

> P1 上传的是 JPEG q95 重编码后的字节流，因此 2.jpg（2 MB 高分 PNG/JPEG）重编码后仅 102 KB；但即便如此，P2 仍比 P1 小一个数量级。

**POOR 弱网下 P2 相对 P1 的加速比**

| 输入图 | P1 (ms) | P2 (ms) | 加速比 |
|---|---|---|---|
| test_img.jpg | 12308.1 | 585.1 | **21.0×** |
| 2.jpg | 2124.1 | 650.6 | 3.3× |
| pre.jpg | 870.0 | 403.2 | 2.2× |
| 1.jpg | 969.6 | 504.3 | 1.9× |

结论：**网络越差，切分收益越大**。5G 下 P1 与 P2 几乎持平（甚至 P1 略优，因为端侧算力被省掉了），而 POOR 下 P2 最多快 21 倍——这正是静态划分必须升级为动态划分（Part C）的量化依据。

> 数据口径说明：云侧耗时当前由 `LocalCloudStub` 在本地等价执行（队员 3 的 FastAPI 服务尚未就绪），因此"云侧"是**保守上界**；真实云端算力更强时，P2 的优势会更明显。云端就绪后用 `--endpoint` 复跑同一矩阵即可替换。

## 5. 实验计划（Part B & C）

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 本地桩与真实云端耗时口径不一致 | 中期报告数据被质疑 | 云端就绪后统一用 `--endpoint` 复跑同一矩阵，两份 CSV 对照 |
| 弱网下 sleep 注入使实验总时长过长 | 跑不完矩阵 | 提供 `--no-sleep` 纯估算模式先扫参数，实测只跑关键格 |
| 识别准确率在切片 JPEG 压缩后下降 | 结论不成立 | 对比 quality 95/85/75 的识别一致率，选临界值 |
| WSL 共享 CPU 导致耗时抖动（实测 ±10 ms） | 单次测量不可信 | 每个组合重复 3 次取中位数；终期前在物理机复测一组对照 |
| 早期 dev 文档数据（det 48%）与实测（19%）打架 | 报告自相矛盾 | 已在 §3.3 明确标注实测口径，早期数据仅作历史参考 |
| 测试样本仅 7 张且分辨率分布不均 | 结论泛化性不足 | 补 20+ 张真实场景图后重跑矩阵 |
